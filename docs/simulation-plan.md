## 选定的仿真栈与已核实的可行性（USER-SIM-20260906-02）

2026-09-06 用户选定：**Gazebo + ROS 2**；本轮范围为**可达性与碰撞、相机 RGB-D 合成图、三块序列端到端，接触物理只做方案一钩取**；模型**暂不归档**，只记提交号。用户进一步明确“吸盘不适合做仿真”（USER-SIM-20260906-03），因此方案二侧吸不建立仿真接触/真空模型，改由实物台架和实机验证气密、抗滑、力矩与释放。

### `aubo_type:=aubo_S3` 可以直接用

`aubo_gazebo/launch/aubo_gazebo.launch.py` 的 `description_file` 默认是 `aubo_ros2.xacro`，并把 `aubo_type`（默认 `aubo_i5`）作为 xacro 参数传下去；`aubo_ros2_macro.xacro` 据此 include `urdf/${aubo_type}.urdf.xacro`。

仓库里**没有任何 `.urdf.xacro` 文件**（`aubo_i5.urdf.xacro` 和 `aubo_S3.urdf.xacro` 均 404）。它们由 **colcon build 时执行的 `xacro.sh` 生成**：`aubo_description/CMakeLists.txt` 在 `ROS_VERSION==2` 时 `execute_process(COMMAND bash xacro.sh)`，脚本把 `urdf/*.urdf` 复制成 `*.urdf.xacro`、在第 2 行注入 xacro 命名空间、删掉所有 `<property>` 行。本次在本机对 `aubo_S3.urdf` 复现了该变换，产物是合法 XML。**结论：`aubo_type:=aubo_S3` 无需额外建模型文件。**

三个连带结论：

- `xacro.sh` 用 `find ./ -type f -name "*.urdf"`，**符号链接不匹配** —— `aubo_S3_10`、`aubo_S3_T0` 不会生成 `.urdf.xacro`，这两个名字不能传给 `aubo_type`，只能用 `aubo_S3`。
- `xacro.sh` 删除的 `<property>` 行里带着 S3 的电机常数与减速比（J1–J3 ratio 121、J4–J6 ratio 101），**仿真模型会丢掉这些**；需要时回原 `aubo_S3.urdf` 取。
- `aubo_gazebo/config/aubo_controllers.yaml` 列的 6 个关节名与 `aubo_S3.urdf` 完全一致，控制器配置可原样复用。

### 踩到的坑（均已固化进 launch）

0. **`GAZEBO_*` 路径必须自己补齐——这条最要命，且会伪装成「已经跑通」。** 本机从未 source `/usr/share/gazebo/setup.sh`，`GAZEBO_MODEL_PATH`、`GAZEBO_RESOURCE_PATH` 全空，于是所有 `model://` 解析失败：`aubo_description` 的 STL **碰撞网格根本没加载**，`sun`/`ground_plane` 也找不到。gzserver 对此只打一行 `[Err] Failed to find mesh file` 就继续跑，控制器照常 active、关节照常到位——**首轮「跑通」的结论因此是不完整的：当时机器人在仿真里没有任何碰撞体**。直到把场景加进来、发现电池一路自由落体到 −6000 m 才暴露。现在 launch 里追加三条路径：`/usr/share/gazebo-11`（resource）、`/usr/share/gazebo-11/models`、含 `aubo_description/` 的 share 目录，以及本包 `models/`。注意必须用 `AppendEnvironmentVariable`，用 `SetEnvironmentVariable` 会把 gazebo 自带路径整个覆盖掉。
1. **`GAZEBO_MODEL_DATABASE_URI` 必须置空。** 否则 gzserver 卡在拉取已下线的 `models.gazebosim.org`，症状极具迷惑性：`spawn_entity` 报 `Successfully spawned entity`，但模型根本没插入、`gazebo_ros2_control` 插件不加载、`controller_manager` 节点不出现，且 gzserver 日志**不报任何错**。置空后插件立刻正常加载。
2. **`GAZEBO_IP` 要固定为 `127.0.0.1`。** 否则 gazebo 把 master 公布到 WSL 的 `10.255.255.254`，`gz model`、`gz topic` 等命令行工具全部连不上。

另有一处与 WSL 无关：`colcon build --symlink-install` 会失败。`aubo_description/meshes/` 下有 82 个**目录级符号链接**（如 `aubo_i10HL` 指向其他机型），ament 的符号链接安装在这些路径上创建失败。用普通 `colcon build`（拷贝安装）即可。

- **与本文运动学计算交叉验证通过**：零位时 Gazebo 的 TF `base_link→flange` 为 (0.000, −0.256, 0.807) m，与独立 FK 算的 (0, −0.2562, 0.8072) m 一致；把「P2 外框最远角、法兰高 250 mm」那组解发给控制器，实测法兰落在 r=526.8 mm（目标 526.9）、高 250 mm、工具轴下倾 0.49°（约束 ≤0.5°）。前一节的可达性结论至此在真实 ROS/Gazebo 栈里得到复核。

注意 `/joint_states` 里的关节顺序是 `[shoulder, foreArm, wrist1, upperArm, wrist2, wrist3]`，**与 URDF 定义顺序不同**，按下标取值会错位，必须按 `name` 字段匹配。

对应推进顺序的第 0–2 步已完成。

## 场景资产（2026-09-06 已完成）

### 生成方式

场景由 `meituan_sim/scripts/gen_scene.py` 生成，不手写 SDF——底图坐标一旦复核有变，重跑脚本即可。坐标直接取自 MAP 的 PDF 矢量图元，不从预览图量。

世界系以**机械臂底座参考圆圆心为原点**，z=0 为工作台面：

```
x_world = (mx - 393.0) / 1000
y_world = -(my - 439.6) / 1000     # 页面 y 向下，取负转成右手系
```

本轮直接用 `ground_plane` 当台面（机器人底座固定在 z=0），没有单独建桌子。这样「法兰高度」与前文可达性实算里的定义完全一致；代价是没有桌沿和桌腿，工具撞桌边这类情况暂时验不了。

### 生成的资产

| 资产 | 说明 |
| --- | --- |
| `models/battery_{red,yellow,green,blue}` | 本体 70×80×50、横梁 70×26×10（顶面 z=80）、两立柱各 10×26×20（z 50→70），孔口净高 20。质量 0.225 kg（FAQ p5 的 200–250 g 取中值），惯量按整体外包络的箱体近似 |

`ros2 launch meituan_sim s3_gazebo.launch.py task:=p1|p2` 切换任务页，默认 `p2`。

电池颜色取 **红/黄/绿/蓝**——依据是 FAQ 的口令示例「任务1：抓取红色电池放入 T0；任务2：分别抓取"黄-绿-蓝"电池放入对应位置」，恰好四色且与「4 块颜色不同」吻合。但这仍是**示例不是规格**，实物颜色及色号待核（Q08）；A/B/C/D 位与颜色的对应关系是本项目为便于仿真自定的，正式对应由比赛日口令决定。

### 底图为什么改用几何体而不是贴图

初版把底图 PDF 渲染成 2048×1580 的纹理贴在薄盒体上。开 GUI 一看就发现印刷内容和实际坐标对不上：**印刷的电池摆放区跟电池模型不在同一处**。

排查过程值得记，因为第一反应是错的：

1. 肉眼判断「贴图镜像了」，做了水平翻转——**这是错的**。那次「镜像」是斜视角造成的错觉，翻转反而把本来对的左右关系弄反了。
2. 改用确定性方法：在贴图上印三个基准点（世界原点、电池 A 中心、P2 内框中心），渲染后用连通域自动定位；再以**位置已数值验证过的四块电池模型**标定「世界→像素」，反解每个基准点的实际世界坐标。
3. 解出的仿射**行列式为负**——是镜像叠加旋转，不是单纯转 90°。实测偏差最大 **454 mm**。
4. 补偿方案是「盒体尺寸互换 0.540×0.700 + 模型 yaw=π/2 + 贴图逆时针 90°」，偏差降到 46–86 mm，但**没能归零**。

于是放弃贴图，改为按 PDF 矢量坐标直接生成几何体：底板、电池摆放区、4 个电池位、T0 与 P1–P3 外框、P1–P3 内框圆、底座参考圆，各自一个 visual，坐标全部走同一个 `w(page_mm)` 换算——**按构造即精确**。渲染实测内框圆位置误差 4.5–8.9 mm，且这点残差来自机械臂遮挡使圆域被裁、质心偏移，不是模型误差。

之所以值得花这个功夫：**P1–P3 内框圆正是 70% 覆盖率的判定基准**。印刷位置偏几厘米，肉眼判断「电池有没有放进框里」就会被误导，而这是计分项。代价是几何体没有中文标注文字。

### 场景验证结果

| 检查项 | 结果 |
| --- | --- |
| 4 块电池落位 | x/y 与设计值完全一致，z ≈ −2e−6 m（稳定停在台面） |
| 底图几何对齐 | 渲染实测内框圆位置误差 4.5–8.9 mm（残差来自机械臂遮挡造成的质心偏移） |
| 机器人碰撞网格 | `gz model -i` 中 14 处 STL 引用，全部解析成功，零 `[Err]` |

| 位姿精度 | 全部 7 个位姿实测 xy 误差 ≤ 0.71 mm（其中多数是 `tf2_echo` 只打印 4 位小数造成的 0.1 mm 量化），高度精确 250.0 mm |

## D435i 相机（2026-09-06 已完成）

### 建模方式

`urdf/d435i.urdf.xacro` 提供 `d435i` 宏，挂在 `flange` 上（眼在手上，USER-HW-20260906-03）。

Gazebo Classic 的单个 depth 传感器只有一个视场，而 D435i 的**彩色 69°×42° 与深度 87°×58° 并不相同**（RS-D435I）。为保留这个必须按共同有效视野核验的事实，这里建成**两个传感器**：`camera` 型出彩色（水平 69.4°），`depth` 型出深度（水平 87°）。实测 `camera_info` 反算出的视场为彩色 69.4°、深度 87.0°，与设定一致。

| 项 | 取值 | 依据 |
| --- | --- | --- |
| 安装位姿 | 相对 `flange` 平移 (0.07, 0, 0.03) m、`rpy=(0, −π/2, 0)`，使光轴与工具轴同向 | **占位值**，实物支架未定（Q04）；改这一处即可 |
| 彩色 / 深度分辨率 | 均 640×480 @30 Hz | 先取小分辨率保 WSL2 帧率，可调 |
| 最小深度 | `min_depth` 0.28 m | RS-D435I 给出的最大分辨率下最小深度 |
| 相机本体 | 25×90×25 mm 盒体，0.072 kg | D435i 外形量级 |

话题名由 `<sensor name>` 决定，插件**不接受 `~/` 形式的 remapping**（试过，无效）：

- `/d435i/color/image_raw`、`/d435i/color/camera_info`
- `/d435i/depth/depth/image_raw` ← **深度图**（32FC1）
- `/d435i/depth/image_raw` ← 深度相机出的彩色图，不是深度
- `/d435i/depth/points`

### 验证结果

把机械臂移到电池上方观察位（法兰高 450 mm、工具轴竖直向下），实测：

| 检查项 | 结果 |
| --- | --- |
| 出图 | 彩色 640×480 `rgb8`、深度 640×480 `32FC1`，深度有效率 100% |
| 视场 | 由 `camera_info` 反算：深度 87.0°、彩色 69.4°，与官方规格一致 |
| 深度绝对精度 | 相机光心离台面 0.4199 m（TF 真值），深度中心读数 0.3699 m，差 **恰好 50.0 mm** = 电池本体高度 |
| 反投影链路 | 按 `p_base = T_base_cam · p_cam` 反投影：中心像素落在 **z = 0.0500 m**（电池本体顶面，且 x/y 落在绿电池足迹内），另取三个像素均落在 **z ≈ 0.000 m**（台面） |
| 颜色可分性 | 一帧内四色像素均被阈值分出：红 8874、黄 8593、绿 9278、蓝 9949 |

反投影结果说明 [硬件与传统视觉方案](hardware-vision-plan.md) 里约定的 `p_base = T_base_flange(t) · T_flange_camera · p_camera` 这条链路在仿真中是通的，可以直接拿来做识别/定位算法的回归。

### 一个由此暴露的设计约束

`min_depth` 0.28 m 不是摆设：**抓取位不能兼作观察位**。前面验证的抓放位姿是法兰高 250 mm，相机比法兰低 30 mm，即 220 mm < 280 mm，深度在那个高度上直接无效。另一方面观察位也不能任意抬高——在电池 A 的半径 428 mm 上，法兰高 600 mm 已超出竖直向下姿态的可达范围（实测求解不收敛），450 mm 可解。**观察位窗口被下有最小深度、上有可达性两头夹住**，这与方案里"下探时若目标进入深度近距无效区，使用已在有效观察位确认的基座坐标完成接近动作"的写法一致，现在有了具体数字。

### 仿真没有建模的部分

用仿真结论推实机前必须记住：无 IR 散斑投射器、无立体匹配，深度是渲染出来的理想值——**没有空洞、没有边缘混合像素、没有反光失效、没有噪声**，有效率 100% 在实机上不会出现。彩色与深度光心之间的实际外参这里取 0，实机须以标定为准。支架未定，安装位姿是占位值。

## 视觉管线与回归（2026-09-06 已完成）

### 包与分层

视觉代码放在**独立的 `meituan_vision` 包**，不放进 `meituan_sim`——它不依赖仿真，接实机 RealSense 时只需 remap 话题。

- `meituan_vision/detector.py`：纯 numpy/OpenCV，无 ROS 依赖，可离线回放与单测。
- `meituan_vision/regression.py`：抓一帧，与底图真值比对，打印回归表，退出码即判定。
- `config/colors.yaml`：HSV 阈值；`config/ground_truth_p2.yaml`：真值，与 `gen_scene.py` 同源。

### 管线

HSV 分割（红色跨 H=0 用两段）→ 形态学开闭 → 连通域 → **彩色像素映射到深度像素** → 反投影到基座系 → **按高度分层** → 最小外接矩形拟合足迹与朝向。

两处值得记的处理：

1. **高度分层定姿**。按 `battery-geometry.md` 说的「模型包含两个明显的高度层」，把反投影点按 z 分成本体顶面（0.030–0.066 m）与提手横梁顶面（0.066–0.095 m），分别拟合。实测本体顶 z 恒为 0.0500、提手顶恒为 0.0800，与设计值一致，这一层同时充当了检测正确性的自校验。
2. **彩色↔深度像素映射**。彩色 69.4° 与深度 87° 视场不同，需按内参做映射。当前实现假设**两光心重合**——仿真里成立（外参取 0），**实机不成立**：D435i 彩色与深度光心有基线，必须先做深度对齐（librealsense 的 align，RS-ALIGN）。这一条已写在模块 docstring 里。

### 回归结果

四块电池、四个观察位（电池 A 上方 450 mm、电池 D 上方 450 mm、中心上方 500 mm、中心上方 400 mm），共 16 次检测：

| 指标 | 结果 |
| --- | --- |
| 检出率 | 16/16，零误检（每帧候选恰好 4 个） |
| 相对底图真值的定位误差 | **0.8 – 1.9 mm** |
| 跨观察位一致性 | 每块电池 σx ≤ 1.07 mm、σy ≤ 1.07 mm，四视角最大分散 **≤ 2.86 mm** |
| 朝向 | 89.9 – 90.2°（真值 90.0°） |
| 高度层 | 本体顶 0.0500 m、提手顶 0.0800 m，逐帧一致 |
| 足迹拟合 | 77.4–79.4 × 67.8–69.7 mm（名义 80×70） |

跨观察位一致性这一项，正是 [硬件与传统视觉方案](hardware-vision-plan.md) 第 3 节要求的「同一固定目标经不同末端观察位变换后应得到一致的基座位置」，现在在仿真中成立。

足迹拟合系统性偏小 1–2 mm，原因明确：采样前对掩膜做了 5×5 腐蚀以避开物体边缘的深度混合像素，代价是足迹被削掉一圈。这是可修正的已知偏差（用未腐蚀掩膜拟合轮廓、只用腐蚀掩膜取深度即可），当前不影响中心定位。

把这个精度放到任务判定上看：内框 70% 覆盖率的容差是沿 x ±17.26 mm、沿 y ±18.19 mm（见前文实算），而视觉定位误差在 2 mm 量级——**在仿真条件下视觉不是精度瓶颈**。

### 这个结果不能证明什么

阈值是在合成图上定的，**不能直接用于实机**：仿真里是纯色渲染，没有环境光变化、反光、阴影、白平衡漂移。深度是渲染的理想值，100% 有效、无噪声、无空洞、无边缘混合像素。外参是真值而非标定结果。因此上表证明的是**算法逻辑与坐标变换链是对的**，不是实机精度。实机必须用 D435i 实拍样本重标阈值并做手眼标定，再重跑同一套回归。

## 钩具与抓放（2026-09-06，部分完成）

### 钩具模型

`urdf/hook.urdf.xacro`，按 [电池几何与抓取分析](battery-geometry.md) 的可逆性检查式取值：承托舌厚 5、上翘尖高 5，合计 10 mm，在 20 mm 名义孔高内上下各留 5 mm 余量；喉深 50 mm（横梁厚 26 mm）；钩柄 12×12；TCP 定在承托舌顶面、沿进钩方向 30 mm 处，啮合时该点位于横梁正下方。

**舌宽是仿真改出来的**：初版取 30 mm，孔口宽 50 mm，左右各留 10 mm。结果电池在舌面上沿横梁长度方向侧滑约 33 mm 直到立柱抵住钩柄，搬运中脱落。加宽到 44 mm 后左右各剩 3 mm，抓取稳定——代价是进钩的横向对准精度要求同步收紧到 ±3 mm。这正是文档里「钩具穿孔部分的横向宽度须留出左右定位余量」那句话的定量结果，也说明**上翘尖只挡进钩方向，挡不住沿横梁方向的侧滑**。

### 进钩方向必须按邻居选

初版让所有电池都从 −y 侧进钩，结果钩子撞的是绿电池——p2 布局里红/绿同列、y 向中心距 87.7 mm，而电池深 80 mm，**两块之间只有 7.7 mm 缝隙，根本没有进钩通道**。是靠 Gazebo 的 `/gazebo/task_p2/physics/contacts` 话题抓到接触对才定位的。

现在规划器带通道检查：把钩具从预备位到穿钩位的扫掠区（沿进钩方向 −(退让+柄长) 到 +尖长，横向 ±舌半宽）与其它电池足迹求交，逐个方向试。p2 布局的结论是**远排 A/B 从 +y 侧进、近排 C/D 从 −y 侧进**。这对应 battery-geometry.md 的「须根据周围电池及工具包络选择有通道的一侧」。

### 已验证：单块钩取搬运

红电池 → P1，8 阶段流程（预备 → 穿钩 → 承托提升 → 搬运 → 落台 → 卸载 → 清钩尖 → 退钩）逐点笛卡尔加密后执行：

| 阶段 | 实测 |
| --- | --- |
| 承托提升 | 电池升到 z=0.130 m，正是「横梁下沿 0.070 搭在 TCP 上」对应的悬挂高度 |
| 落台放置 | 落点误差 **3.5 mm**，yaw 0.0° |
| 序列第一块（黄→P1，两次重跑） | 误差 2.1 / 2.9 mm，**内框覆盖率 84.4% / 84.1%，均 ≥70% 达标** |

**固定被动钩在仿真里能真的把电池提起来**，不需要任何抓取插件——这是钩取方案相对吸附方案在仿真验证上的一个实际便利。

### 三块连续序列：已跑通，但成功率不齐

之前卡在段间位形翻转。真因比"翻转"更根本：**IK 完全没有碰撞意识**。Gazebo 接触日志显示钩具↔大臂自碰 11.9 万次、相机↔大臂 1.7 万次，而且 `upperArm_Link` 直接扫到桌面上的蓝、黄电池——锁定的那个 IK 分支本身就是自碰的折叠位形。

解决办法是给 IK 加碰撞代价：把机械臂近似成一串胶囊，检查非相邻连杆两两最短距离（自碰）、各连杆抬离台面、以及非工具段不得进入电池足迹上方的低空。为控制耗时做两阶段——先不带碰撞代价快速求解，**只对确实碰撞的点**启用碰撞代价重解（全程开启会慢一个量级）；重解时再加一项连续性代价，优先挑离上一位形近的解，避免为避碰跳到别的分支。

配套还做了三件事：

- **锚点串接**：每段以"穿钩"为锚点，且继承**上一段的锚点**（而非上一段末位形）。三段锚点都是低位穿钩姿态、几何相近，这样能把整条序列锁在同一 IK 分支。段内关节跳变从上百度降到 6–14°。
- **跳变插值**：仅剩的一处 349° 位形切换发生在 z=0.25 的安全高度，改为每步 ≤8° 的关节插值并逐点验碰撞（43 步，0 碰撞）。
- **起始位形**：不再用"固定就绪位 + 关节桥接"（那段插值实测 12/36 步碰撞），改为把**计划首点的位形直接写进 URDF 的 `initial_value`**，机器人开机即在位，桥接彻底免掉。

最终 461 个路点**全部无碰撞**（0/461）。序列能完整跑完。

| 黄 → P1 | **6/6** | 2.0 – 2.5 mm | 84.2 – 84.4% |
| 绿 → P2 | **6/6** | 10.8 – 11.5 mm | 77.0 – 77.7% |
| 蓝 → P3 | **2/6** | 成功时 11.4 / 11.8 mm | 76.7 / 77.1% |

黄绿两块稳定达标。蓝块四次失败**落点高度一致**（(0.076,0.254)、(0.045,0.253)、(0.047,0.255)、(0.073,0.228)），说明不是随机物理。

### 蓝块为什么掉：余量算不过跟踪误差

针对蓝块搬运段单独抓接触日志，期间只有钩具↔蓝块和蓝块↔地面两种接触，**没有任何第三方碰撞**——它是从钩上滑脱的，不是被撞掉的。

根因是量级对不上：**舌宽 44 mm 在 50 mm 开口里只剩 ±3 mm 横向余量，而控制器运动中的跟踪误差实测有 4–6 mm**。进钩时若没坐正，立柱骑在舌沿上，搬运中就会滑脱。

试过两个办法，都**没能**解决：

- 把限速从 0.55 降到 0.35 rad/s（排除惯性因素）——蓝块仍在同一位置掉落。
- 在预备、穿钩、承托提升、落台、卸载各加 1.0–1.5 s 驻留等跟踪误差收敛——第一次全达标，但连续复跑两次蓝块仍失败。

注意这个 ±3 mm 是**自己造成的**：舌宽 30 mm 时电池会侧滑 33 mm 脱落，加宽到 44 mm 治好了侧滑，却把插入对准要求收紧到了 ±3 mm。两个失效模式在舌宽这一个参数上互相拉扯。

### 下一步该往哪走

2026-09-07 审计补充：下列视觉改进仍是待验证方案。视觉定位误差不能替代工具相对提手的总误差预算；单次预校正不保证消除运动跟踪误差，近距深度与姿态/外参误差也需考虑，不能据 0.8–1.9 mm 定位结果断言闭环插入必然成功。详见 [Demo 录制评估](demo-readiness.md)。

候选办法按可信度排：

1. **视觉闭环插入**（推荐）。当前是纯开环——按底图设计坐标进钩，不看电池实际在哪。而本项目的视觉管线定位精度是 **0.8–1.9 mm**，远小于 ±3 mm 余量。在进钩前用末端相机测一次电池实际位姿并修正，正是眼在手上这套配置存在的意义。**仿真到这一步反过来论证了视觉投入的必要性**：不是锦上添花，是这个余量下的必需品。
2. **钩具几何**：舌片前缘加导入倒角/斜面，让插入时能自对中，把"对准精度"换成"自纠偏能力"，绕开舌宽这个单参数的两难。
3. **改用 MoveIt 规划**：碰撞问题已由自写的胶囊检查解决，MoveIt 的增量价值主要在更好的路径质量与标准化，不再是阻塞项。

蓝块的 2/6 是**当前实现**的成绩，不是钩取方案的上限——它衡量的是开环精度，不是钩子本身能不能用。

### 顺带记录的两个现象

历史现象说明（2026-09-07 补注）：以下自碰发生在早期调试阶段；当前序列已有上节所述修复记录，不能把历史接触次数当成修复后每次运行的现状，也不能把离散路点检查推广为任意轨迹的安全保证。

- 接触数据显示 `hook_link` 与 `upperArm_Link` 之间有持续接触（数万次），即钩具在某些位形下贴到大臂。SRDF 的 `disable_collisions` 只有 9 对且不含钩具，加装工具后须按文档要求重新生成自碰撞矩阵。
- 电池被深度挤压时 ODE 会数值发散（位置跳到几米甚至十几米外）。看到这种数值就该判为仿真失效，不能当成「抛飞距离」读。

| 部分 | 状态 |
| --- | --- |
| S3 连杆几何、惯量、关节限位、可视/碰撞网格 | 仓库提供，可直接用 |
| MoveIt 规划组与自碰撞矩阵 | SRDF 提供，但 `disable_collisions` 只有 9 对，加装工具后须重新生成 |
| **末端工具帧** | 分两条路径：纯 `aubo_S3.urdf`/`.srdf` **没有**（链止于 `wrist3_Link`，`end_effector` 为空）；走 ROS 2 的 `aubo_ros2_macro.xacro` 时**有** `ee_link`（fixed 到 `wrist3_Link`，`rpy="0 0 π/2"`，10 mm 盒碰撞，origin x=−0.01）。钩具 TCP 仍建议另加帧，不要改 `ee_link` 语义；那个 π/2 的 z 旋转必须写进 TCP 约定 |

| 道具电池、底图、桌面 | 无，须按 BATTERY-DRAWING 名义几何和 MAP 底图自建 |

## 与实机方案的衔接约定

- **坐标系**：仿真沿用 [硬件与传统视觉方案](hardware-vision-plan.md) 的 `T_A_B` 约定与 `p_base = T_base_flange(t) · T_flange_camera · p_camera`。URDF 的链末端是 `wrist3_Link`，须显式声明「flange = wrist3_Link」或自加 flange 帧，并在仿真与实机使用同一定义，否则手眼外参不可互换。
- **名义模型 ≠ 实机**：仓库 URDF 是名义几何。README 提供 `scripts/calibrate_urdf_dh.py`，从机器人 RPC 读取 DH 校准补偿生成校准版 URDF（需 `numpy` 与可导入的 `pyaubo_sdk`，须传 `--robot-ip`，可带 `--temperature`）。**本机当前没有 `pyaubo_sdk`**（ENV-LOCAL-20260906），且未连接实机，该步骤暂不可执行。仿真结论在完成这一步前不能当作实机精度依据。
- **换工具**：仿真范围固定为方案一钩具；不为方案二建立吸盘真空/接触物理模型。若仅做侧吸支架的几何占位，仍须改 TCP 并重新生成自碰撞矩阵，但这不代表吸附能力仿真有效；相机相对法兰的固定关系改变时，实机需重做手眼标定（Q04）。

## 仿真能回答与不能回答的问题

| 可用仿真验证 | 必须实物/实机验证 |
| --- | --- |
| 底图各目标位的可达性与关节限位余量（已用名义模型实算，见上节） | 提手承载、钩具挠度与止退是否有效 |
| 工具与电池、已放电池、桌面的碰撞与自碰撞（方案一钩具） | 方案二吸盘气密性、真空建立/保持、抗滑与抗剥离；用户明确不做吸盘仿真 |
| 进钩/退钩通道、侧向接近与撤离路径的运动学包络 | 单钩吊挂摆动、吸盘压缩与滑移 |
| 三块序列摆放的路径规划与任务状态机逻辑 | D435i 实际深度噪声、反光、颜色阈值 |
| 内框覆盖率的几何评估（理想姿态下） | 释放后的实际落点与滑移，即 70% 判定的真实结果 |

仿真中 `T_flange_camera` 与物体位姿是已知真值，适合做识别/定位算法的回归测试；但**用真值跑通不等于标定与视觉在实机可用**。
